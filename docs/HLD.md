# HLD: архитектура LlamaPanel

[Документация](README.md) · [Экземпляры серверов](instances.md)

## Назначение и границы

LlamaPanel управляет локальными процессами `llama-server` на машине с бинарником
llama.cpp и GGUF-файлами. Панель предоставляет интерфейс настройки, управления
процессами и просмотра логов. Внешние клиенты обращаются непосредственно к API
нужного экземпляра `llama-server`; панель не проксирует генерацию.

## Компоненты

| Компонент | Ответственность |
|---|---|
| `run.py` | Подготовка `.venv`, загрузка конфигурации и запуск Uvicorn |
| `backend/app/main.py` | Фабрика FastAPI и жизненный цикл объектов приложения |
| `backend/app/settings.py` | Неизменяемый объект `Settings`; приоритет CLI → INI → окружение → дефолты |
| `backend/app/instances.py` | `InstanceRegistry`: конфигурации, резервирование портов, восстановление процессов |
| `backend/app/process_manager.py` | Отдельный `ProcessManager` для каждого экземпляра: процесс, состояние, очередь перезапуска и логи |
| `backend/app/llama_client.py` | HTTP-проверки `/health` и `/slots` экземпляров |
| `backend/app/discovery.py` | Обнаружение внешнего процесса для совместимости с прежним одиночным сервером |
| `backend/app/gguf_scanner.py` | Сканирование моделей и LoRA, чтение нужных метаданных GGUF |
| `backend/app/introspection.py` | `BinaryInspector`: чтение и кэширование `--version` и `--help` |
| `backend/app/flags.py` | `FlagCatalog`: схема формы, сопоставление ключей, сборка и разбор аргументов |
| `backend/app/presets.py` | Общая библиотека пресетов |
| `backend/app/storage.py` | Версионированные JSON-документы, миграции и атомарная запись |
| `backend/app/deps.py` | Доступ роутеров к объектам приложения и выбранному менеджеру |
| `frontend/src/App.tsx` | Обзор экземпляров и отдельные рабочие области с конфигурацией, статусом и логами |

Объекты создаются в `lifespan` и доступны через `app.state`. `ManagerDep`
выбирает менеджер по `instance_id`; при отсутствии параметра используется
`default`. Библиотеки моделей и пресетов, схема флагов и бинарник общие.

## Жизненный цикл экземпляра

У каждого экземпляра свои PID, порт, флаги, очередь перезапуска и файл логов.
После запуска состояние `starting` сохраняется, пока `/health` не подтвердит
готовность. `running` означает готовность сервера; неожиданный выход процесса
переводит его в `crashed`.

Если `/slots` подтверждает активную генерацию, перезапуск откладывается до её
завершения. Если занятость определить не удалось, перезапуск допускается сразу.
Очередь и её отмена относятся только к выбранному экземпляру.

Закрытие панели оставляет процессы работающими, но отменяет отложенные
перезапуски. При следующем запуске реестр проверяет сохранённые PID, время
создания и идентичность исполняемого файла перед подхватом. Проверка времени
создания также защищает остановку подхваченного процесса от повторного
использования PID. Остановленные экземпляры автоматически не запускаются.

## Флаги и пресеты

Схема формы строится по `--help` установленного бинарника. Слой `CURATED`
добавляет подписи, базовые группы и стабильные ключи, а `HIDDEN` исключает
управляемые панелью параметры. Если бинарник недоступен, используется снимок
`backend/app/snapshots/llama-server-help.txt`.

Форма хранит только явно заданные переопределения. `build_args` передаёт их,
включая значения, совпадающие с документированными дефолтами. Пустые значения
не передаются; булева пара использует нужное написание `--x` или `--no-x`,
повторяемый флаг передаётся для каждого элемента. Модель и порт задаёт панель.
Порт принадлежит экземпляру и не заменяется портом из пресета.

`parse_args` восстанавливает флаги из командной строки подхваченного процесса.
Старые пресеты сохраняют свои значения: определить, какие из них пользователь
ввёл вручную, невозможно. Сопоставление ключей и миграции описаны в
[конфигурации и хранении данных](configuration.md).

## Модели и интерфейс

Основное название модели берётся из имени файла без `.gguf`; для составных
GGUF используется общий префикс без номера части. `general.name` сохраняется
отдельно и показывается в подробностях Models вместе с архитектурой,
квантизацией, контекстом и файлами.

REST API передаёт состояние и конфигурации, WebSocket — логи выбранного
экземпляра. Типы frontend генерируются из OpenAPI. Черновики сохраняются при
переходах между экземплярами в текущей вкладке браузера; постоянная запись
выполняется через Save configuration, Start или Apply & restart.

## Ограничения

На одну директорию данных рассчитан один процесс панели. Порты резервируются
между сохранёнными экземплярами, в том числе остановленными. Проверка порта
перед запуском не исключает, что его займёт внешний процесс сразу после проверки.
Панель не распределяет GPU-память: число одновременно работающих моделей
ограничено доступными ресурсами.
