# LlamaPanel

Model-serving панель для `llama-server` (llama.cpp): сканирует директорию с GGUF-моделями,
запускает/останавливает сервер с выбранными флагами, показывает статус и живые логи.
Сам `llama-server` поднимает OpenAI-совместимый API на своём порту — на него может
указывать любой внешний клиент/агент (например Hermes), не зная о деталях запуска.

Панель рассчитана на то, что она **работает на той же машине, где лежат
llama.cpp и модели** (там, где GPU) — процесс `llama-server` запускается как
локальный сабпроцесс.

## Установка на GPU-машине

Фронтенд уже собран и закоммичен в `frontend/dist/` — на целевой машине нужен
**только Python 3.12+**, Node.js не требуется.

```bash
git clone <repo> LlamaPanel
cd LlamaPanel
cp config.example.ini config.ini
# отредактировать config.ini: models_dir, server_bin, host/port
python run.py
```

Вместо `config.ini` те же параметры можно передать разово через CLI-флаги
(`--models-dir`, `--llama-bin`, `--host`, `--port`, `--data-dir`) — они всегда
побеждают файл. Приоритет: **CLI-флаг > `config.ini` > переменная окружения >
встроенный дефолт**. `config.ini` в `.gitignore` — свой путь к моделям туда
пишешь один раз на машине и не таскаешь в git.

Первый запуск сам:
1. создаёт venv в `./.venv` (используя тот Python, которым запущен `run.py`);
2. переисполняет себя внутри этого venv;
3. ставит туда зависимости backend'а (`pip install -r backend/requirements.txt`).

На системный Python это ничего не ставит — только на его основе создаётся
изолированный venv. Повторные запуски — быстрый no-op (venv и зависимости уже
на месте). Открыть `http://<ip-этой-машины>:8000` (или `--host 0.0.0.0`, если
нужен доступ не только с localhost).

Параметры можно задать и через переменные окружения вместо флагов:
`LLAMA_MODELS_DIR`, `LLAMA_SERVER_BIN`.

## Разработка (фронт + бэк раздельно, с hot reload)

```bash
# backend
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

# frontend (в другом терминале)
cd frontend
npm install
npm run dev   # http://localhost:5173, проксирует /api на :8000
```

После пуша изменений `frontend/src/*` (и смежных файлов) в `main` GitHub
Actions ([.github/workflows/build-frontend.yml](.github/workflows/build-frontend.yml))
сам пересобирает `frontend/dist` и коммитит его обратно в репозиторий -
руками пересобирать перед деплоем не нужно, достаточно сделать
`git pull` на GPU-машине после того, как workflow отработает.

Если нужно собрать локально (например, чтобы проверить сборку до пуша):

```bash
cd frontend && npm run build
git add dist && git commit -m "rebuild frontend"
```


## Что уже есть (MVP)

- Сканер `*.gguf` с группировкой мультичастевых моделей (`name-00001-of-000NN.gguf`)
  и чтением метаданных из заголовка GGUF (архитектура, квант, context length) без
  загрузки самой модели.
- Единая декларативная схема флагов (`backend/app/flags.py`) — фронт рендерит форму
  по ней, а не дублирует список полей руками.
- Старт/стоп `llama-server` как дочернего процесса, статус (stopped/starting/running/
  stopping/crashed).
- **Пресеты**: сохранение модели + набора флагов под именем в `data/presets.json`
  — переживает перезапуск скрипта и перезагрузку машины.
- **Автоопределение уже запущенного `llama-server`**: если панель перезапустили, а
  процесс остался жив (или его подняли вручную из терминала), при следующем опросе
  статуса панель находит его через `psutil`, разбирает его argv обратно во флаги и
  подтягивает в UI — модель и значения флагов не нужно вводить заново. В статусе
  такой процесс помечен как `adopted`; `Stop` в UI всё равно его останавливает.
- **Логи всегда идут в файл** (`data/llama-server.log`), а не только в PIPE —
  поэтому даже "усыновлённый" процесс, за которым панель не следила с самого начала,
  можно дотейлить: если это был процесс, запущенный самой панелью в прошлый раз,
  лог не прервётся при перезапуске скрипта. Если модель запущена вручную мимо
  панели (не через наш `--model`/редирект вывода в этот файл), логов для неё не будет
  — только сам факт, что она обнаружена и её флаги распознаны.
- Единая точка входа (`run.py`) и деплой без Node.js на целевой машине.
- **Reload без обрыва инференса**: кнопка `Reload` применяет изменённые флаги
  (`--ctx-size`, `--seed` и т.д. — всё, что требует перезапуска процесса)
  безопасно. Перед рестартом панель спрашивает у самого `llama-server` через
  его собственный `/slots`, идёт ли сейчас генерация — независимо от того, кто
  её вызвал (Hermes, встроенный webui llama.cpp, curl). Если сервер занят,
  рестарт откладывается ("reload queued") и применяется автоматически сразу
  после завершения текущего запроса; UI показывает баннер с возможностью
  отменить отложенный рестарт. Ни Hermes, ни webui не должны ничего знать об
  этом механизме — никакого дополнительного сигнала с их стороны не требуется.
